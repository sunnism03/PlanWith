# Performance Fixture Policy

## Scope

This policy applies to Chatbot C1 baseline and after runs against a deployed
test environment. Production data and shared user data are out of scope.

## User and Category fixtures

- Prefer a fixed set of pre-provisioned performance users and their default
  Categories.
- Keep the same user IDs and Category IDs for baseline and after so data shape
  remains comparable.
- Refresh JWTs immediately before a run and keep them only in ignored
  `users.csv` or runtime files.
- Do not call `bootstrap-user.sh` during a measured run against a shared DB.
  That script creates a User and a default Category for every row.
- Local isolated H2 dry runs may create fixtures because the complete database
  file is disposable.
- Deployed fixtures are retained as named performance fixtures. They are not
  deleted after each run.

## Data safety

- Every designated performance user must have zero Personal Event and Personal
  Todo rows in the C1 scenario month before warm-up.
- The same counts must remain zero after the measured run.
- C1 stages Chatbot data in Redis but must not persist Event or Todo rows.
- Existing users, Categories, Events or Todos in a shared DB must never be
  deleted by the harness.
- If temporary deployed fixtures are ever required, create them only in a
  dedicated test DB with an explicit user-ID allowlist and a separately
  approved cleanup procedure. Do not infer deletion scope from an email prefix.

## Redis fixtures

- Record each response token generated by the current run.
- Resolve each token to exactly one `chatbot_token:<token>` key and one
  `chatbot:<payload-id>` key.
- Verify existence and positive TTL before cleanup.
- Delete only keys listed in the current run's ignored exact-key ledger.
- Verify those exact keys are absent after cleanup.
- Wildcard, `SCAN`, prefix-wide deletion and deletion of unrecorded keys are
  forbidden.
